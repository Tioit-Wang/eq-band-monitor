## 1. 辩论中确认的真实缺陷（已修复或待修）

### 1.1 【已修复】热键全哑的 P0 事故

`_on_hotkey` 引用了**从未导入**的 `SCENE_BY_HOTKEY`，求值顺序决定第一行就
NameError。PySide6 对槽函数异常只打 traceback 不中止进程，所以表现是：

    热键注册成功 20 个 → 程序正常运行、频谱照常滚动 → 按任何键都没反应

1.0.0 已带此 bug 发布。**156 项自测全绿、CI 全绿。**

修复要点：改用 `SCENE_BY_KEY`（`SCENE_BY_HOTKEY` 的键是 "F2" 这类热键名，
而回调收到的是注册名 "own"，原代码的 `.upper()` 那半句从未生效过）。

新增防线：
- `check_undefined.py`：AST 静态扫描未定义名字（已反向验证能精确抓回该 bug）
- `selftest_wiring.py` 7 项：静态扫描 + 打桩调用全部 20 个回调 + 名单同步校验
- `_on_hotkey` 增加 `hotkey: <name>` 日志，可区分"按键没进来"与"处理失败"

### 1.2 【已修复】托盘菜单重复条目 + 设备勾选错行

- 托盘里「生成交接包 (F10)」出现了两次。
- `_switch_device` 用**列表下标**比对**设备索引**，而 `list_devices()` 会把
  默认设备排到最前，所以手动切设备时勾会落在错误的行上——恰好发生在
  "采不到声音、手忙脚乱切设备"的时刻。改用 `QAction.setData(d.index)`。

### 1.3 【待修】F10 阻塞 GUI 线程约 4 秒

实测：6 个文件 / 27.2 秒音频 → `build_report` **309 ms**；
按 README 推荐的 12×30s 满配外推 → **约 4089 ms**。

这是 GUI 线程上的同步调用，期间托盘、热键、重绘全停。
`MAX_SECONDS = 30.0` 让这是**合法输入**，不是理论风险。

正方与反方在此达成一致：这是 P0 bug，应独立修。

### 1.4 【待修】启动期同步阻塞约 2.2 秒

`list_devices()`（269ms）+ `pick_best_device()` → `probe_signal()`（1928ms），
且都发生在 `Overlay.show()` **之前**。用户双击 exe 先看到 2 秒无窗口。

更危险的细节：`probe_signal()` 在本机返回
`{0:0.0, 1:4.85e-26, 2:0.0, 3:0.0, 4:9.16e-05}`——
**麦克风的 9e-5 比扬声器大 19 个数量级**，只是靠 `prefer_default` 短路
才没选错。安静房间里启动会选到麦克风。

### 1.5 【待修】报告自称 dBFS 但刻度偏了

`analyze_file` 先 `mono = data.mean(axis=1)` 再算 61 段，而 mono 混合可能
损失 3–6 dB（取决于左右声道相关性）。但 `handoff.py` 写"所有 dB 都是 dBFS
（0 = 满刻度）"。`stereo_corr` 就在同一个数据结构里，却没接进定义。

一个 AI 读到"峰值 −12.3 dBFS"会当成绝对电平用。

## 2. 四个角色的核心主张

### 2.1 用户代表：这是「赛前做一次测量实验」的工具，不是实时助手

**关键校正事实**：主程序**已经不再自己给结论**。`eqsuggest.build_advice`
只被自测引用；F10 只做"分析 → 生成 report.md → 弹窗给路径"。
所以真实旅程是"工具给你一份 10 章报告，你自己或另一个 AI 去读"。

真实旅程里最贵的一步不是按键，是**赌运气**：
12 格矩阵要求等目标声源真实发生。玩家蹲在楼里听到头顶有动静那一刻，
他要先开枪还是先按 F3？**没人会在对枪时按录制键。**

被判定为伪需求的：
| 诉求 | 判决依据 |
|---|---|
| 实时 EQ 建议 | 一局真正需要 EQ 结论的时刻是 0 次；蹲守时弹出"建议砍 4kHz"＝纯噪声 |
| 录音回放 | 真需求是"录到了没有"，不是"听内容"；读一行数据比戴耳机判断快 10 倍 |
| 声源定位/多声道 | 那个 10 点参数 EQ 左右共用，左右能量差**无法用 EQ 修正**——有信息没出口 |
| 云端同步 | 玩家对"上传我游戏音频"的警觉等同于外挂；真需求只是别丢预设，本地 JSON 够 |
| 更多可视化图表 | 悬浮窗每一像素都在挡视野；他需要的是一行字，不是一张图 |
| 凑满 12 格 | `near:walk` 与 `far:walk` 的形状差往往 < 3dB，低于可闻门限 |

**唯一该做的事**：F10 直接给 3 行可执行的增益结论 + 5 秒试听 + 一键撤销。

> 他的痛点是**不敢按应用按钮**，不是缺数据。数据已经够了，
> 缺的是一个敢按下去的按钮。

### 2.2 QA Lead：能跑通 ≠ 能发布

热键事故的根因不是"哪行代码错了"，而是**没有任何测试 `import main`**。
按名字统计触达率：`hotkeys.py` 0/6、`main.py` 0/27。

其余 0 覆盖且坏了立刻被感知的：`capture.py` 端到端（0/16）、
`rawanalyze.build_report`（而 F10 只走这一条路）、`_tick`、`diagnostics.py`、
`advice_window.py` 全模块。

**验收门槛（不满足不合并）**：
1. 纯逻辑改动 → 一条断言**数值**的 check（不接受"能 import"）
2. 入口连通性测试（就是挡本次事故那条，0.1 秒跑完，不启 GUI）
3. 产物有往返断言（写 → 读回 → 断言关键字段）
4. 触及热键/菜单/托盘的改动，PR 里贴手动验证记录

**明确不要加**：pytest-qt 全流程 GUI 自动化、无断言目标的 smoke 测试、
覆盖率百分比门槛——个人项目里维护成本超过收益，且**它们都拦不住本次的 NameError**。

最想补的测试：`selftest_wiring.py`（已实现）。
它挡住的事故类别是：*"整个输入层失效，但所有单元测试全绿、
CI 绿、Release 自动发出去"*。

### 2.3 正方（产品经理）：把「敢不敢按」补上

提案与 RICE：

| # | 提案 | RICE | 一句话 |
|---|---|---|---|
| F1 | 一键落盘 `.fac`（逐段 diff + 备份） | 85.5 | 641.98Hz 这种数字手抄必错，错了还听不出是哪项 |
| F2 | 应用前预演 + 削波预检 | 81 | 唯一攻击"不敢按应用"的功能，**不产生任何声音** |
| F3 | 缺格 → 结论依赖图 | 54 | 把"缺 7 格"变成"所以哪条结论没了" |
| F4 | 改后复测闭环 | 51 | 让工具从"测一次"变成"调音流程" |
| F5 | 回溯录制（环形缓存） | 39.4 | **已被数据否决，撤回** |
| F6 | 同场景多段累积 | 45 | 实为**修 bug**：`clips[key]` 后者覆盖前者 |

**第二轮的三个让步**：
- **F5 撤回**。用现有 12 个真实 WAV 一测就清楚：首起音在中位数 2.5–5.6 秒，
  不是"按下时声音已在播"，而是**用户在等**。环形缓存解决的是不存在的问题。
- **F6 降级**：`recorder.Recorder` 在生产路径永不执行，它属于死代码的一部分，
  不是新功能。
- **F1 降到 0.5 人日**（原提案 1 人周）。原 RICE 口径掩盖了工作量低估。

### 2.4 反方（架构师）：扩张会先撞两堵物理墙

**断裂点 1：GUI 线程 50ms 预算**
现状 4.1ms（analyzer 1.78 + paintEvent 2.32）= 8.2%。
- L/R 双声道 → paintEvent 2.32→4.6ms（线性外推自实测量柱成本）
- 瀑布图 +2~4ms、3D +5~10ms

真正的杀手是 Qt 单线程：一旦单帧超 50ms，`PreciseTimer` 不跳帧而是**堆积**，
连热键响应（`nativeEventFilter`，同线程）一起延迟。

**断裂点 2：F10 阻塞是 O(场景数 × 时长)**——见 1.3。

**断裂点 3：热键预算已用 20 个**
`RegisterHotKey(None, ...)` 是**全局**注册，每个热键都从全系统抢。
F12 已被主动避开是正确的。`Ctrl+Shift+字母` 已占 6 个，
"位置×移动方式"这个绕法已经用掉了"组合键"这一个自由度，**不会有第二个**。

**断裂点 4：配置 1→N 字段**。`settings.py` 无 schema、无版本、无迁移；
`put` 是全量读-改-写，加并发写就互相覆盖。

**准入门槛（5 条全过才配加）**：
1. GUI 单帧 ≤15ms（现 4.1ms，留 2/3 余量）
2. >200ms 的操作必须出 GUI 线程
3. **不新增全局热键，除非先删一个**
4. 逻辑必须落在 `app/` 且不启 Qt 可测
5. 不新增持久化格式，除非同时给迁移方案

**对六条的表态**：
- F1 **支持**（附加要求：备份 + diff 默认开启，写盘失败不可静默）
- F2 **条件支持**（不许变成常驻实时建议面板）
- F3 **支持**（最便宜，`handoff.py` 已有 missing 列表，只需映射到结论名）
- F4 **条件支持**（成本被低估 2–3×，且依赖 F1 已落盘 + 用户重录）
- F5 **条件支持 → 已被正方撤回**
- F6 **支持且优先**（这是修 bug，不是加功能）

**成本低估纠正**：
| 提案 | 正方隐含 | 反方估计 | 倍数 |
|---|---|---|---|
| F5 | 小 | ~300 行 + 架构改动 | 3–5× |
| F4 | 中 | ~400 行 + 双快照对比渲染器 | 2–3× |
| F2 | 中 | ~250 行（含挖出 build_advice） | 1.5–2× |

关键洞察：**F5/F4/F2 都要动数据模型层**，而那层恰恰是 0 测试 + 无 schema 的地方。
具体到 F2：`build_advice` 从 `Recorder`（内存帧）取数，但主流程产物是 WAV 文件
（`rawrec.clips` 是路径）。**两套数据模型不兼容**，不是"挖出来接上"那么简单。

## 3. 交锋中的三个关键裁决

### 3.1 「F2 是否必须排在 GUI 线程改造之后」

- 反方：是。4 秒阻塞会拖垮热键响应。
- 正方：否。**触发阻塞的动作是 F10，而 F10 之后 `activateWindow()` 会主动抢焦点——
  那一刻游戏已经不在前台。** 没人会在交火中按 F10。所以"阻塞导致漏录"的
  因果链需要一个被排除的前提。
- **裁决**：正方这一条成立。但双方都同意 F10 阻塞本身是 P0，应独立修。
  排序为 **①修 F10 阻塞 → ②F2 → ③QThread 化**，而不是把三者捆绑。

### 3.2 「699 行死代码」与「F2 挖回死代码」是否矛盾

- 反方：`eqsuggest.py` + `fit.py` 共 699 行、21.4%，主程序零调用，
  却占用了 `selftest_suggest.py` 231 行的测试注意力。
- 正方：挖回来不等于复活死代码，也可以是**给它装上用户**。若反方坚持，
  更干净的选择是删掉 `eqsuggest.py`，只保留 `peaking_response`。
- **裁决**：反方接受让步——"如果正方接回主流程，'该删'的主张自动失效，
  但'必须接回'的义务同时生效"。**不能出现第三种状态：既不删、也不接。**

### 3.3 「测试全绿」是否还有信息量

热键事故给出了否定答案。正反双方因此都调整了排序：

- 正方：Top 3 从 `F1/F2/F3` 改为 `F10 阻塞修复 → 门禁（已完成）→ F2`
- 反方：认可 `check_undefined.py` 是正确解法，并更正自己"归因为零测试"不完整

## 4. 最终结论

### 4.1 立即做（按顺序）

| 优先级 | 项 | 理由 |
|---|---|---|
| P0-1 | **F10 阻塞修复** | 实测 4.1s 冻结 GUI，合法输入即可触发 |
| P0-2 | **启动阻塞 2.2s + pick_best_device 选错设备** | 首屏 4 秒、安静环境会选到麦克风 |
| P1 | **F2 预演 + 削波预检** | 唯一攻击"不敢按应用"的功能；不碰 paintEvent；输入全已验证 |
| P2 | **F1 一键落盘 .fac**（0.5 人日） | 最高性价比，但救不了核心卡点 |
| P2 | **F6 同场景多段累积** | 实为修 bug：补录会静默丢数据 |

### 4.2 条件支持

- **F3 缺格→结论依赖图**：纯文案/映射改动，零性能风险，可随时插入
- **F4 改后复测闭环**：价值真实，但成本 2–3× 且依赖用户重录；等 F1 落地后再评估

### 4.3 撤回 / 否决

- **F5 回溯录制**：正方用真实数据主动撤回（首起音中位数 2.5–5.6s，
  是"用户在等"而非"按晚了"）
- **实时 EQ 建议**：不是新功能而是产品回滚；20Hz 段单帧抖动 6dB 会让建议每秒跳变
- **录音回放**：字面违反"不产生音频输出"铁律；且 `save_bundle` 已把音频复制到
  `audio/`，用外部播放器即可，**这个需求已被满足，只是没写进 README**
- **多声道/声源定位**：左右能量差无法用共用 EQ 修正——有信息没出口
- **云端同步**：与"不隐藏中间数据"的核心承诺冲突，代码量 50 行 → 5000 行 + 后端
- **瀑布图/3D**：频谱区实测仅 164px，塞不进且与"取时间平均"的设计决定矛盾；
  3D 要撤销 spec 里对 OpenGL 的排除，体积 +15MB

## 5. 可复用的教训

1. **"算得对"和"接得上"是两种测试**。61 段频谱、.fac 字节级往返全对，
   但按键没接上，产品就是废的。
2. **静态检查能挡住 unit test 挡不住的一类 bug**。`compileall` 只查语法，
   查不出未定义名字——而这类 bug 的破坏力是全局的。
3. **记录"谁调用了它"**。699 行死代码之所以危险，不是因为占空间，
   而是因为它持续误导新人和测试注意力。
4. **一个功能的价值 = 收益 ÷ (工作量 × 它挤占的资源)**。
   RICE 的人周口径容易把"接线活"估成天，把"要动数据模型"估成小时。
5. **用户的真实卡点往往在流程末端**。这个工具的测量端已经很硬，
   断点在"给我一个敢按下去的按钮"。
